## 一、一句话架构

```
        ┌───────────────────────────┐
        │  大模型（AIA 统一代理）      │   低频：每 30~90 秒一次
        │  只回答「下一个技能是什么」   │   每次约 1.5k 字符上下文
        └────────────┬──────────────┘
                     │ JSON：{"skill": "...", "args": {...}}
        ┌────────────▼──────────────┐
        │  Planner（planner.py）      │   组装提示词 / 校验 / 兜底策略
        └────────────┬──────────────┘
                     │
        ┌────────────▼──────────────┐
        │  Skills（skills.py）        │   确定性代码：一次调用 = 几十个 API 动作
        │  chop_tree / collect / ... │
        └────────────┬──────────────┘
                     │ API 调用
        ┌────────────▼──────────────┐
        │  McApi（mc_api.py）         │   比赛服 HTTP 客户端（也可换 my_server）
        └────────────┬──────────────┘
                     │ HTTPS
        ┌────────────▼──────────────┐
        │  NMO Bot 接口               │   真正在游戏里动
        └───────────────────────────┘

        旁边还有：
        WorldState（世界状态+记忆，落盘） ← 每圈读写
        Agent（主循环）                   ← 把上面串起来
        Trajectory（轨迹日志）             ← 每步写 jsonl
        Advancements（计分表）             ← 决定「做什么划算」
```

## 二、为什么不像旧版那样「一个动作问一次」

旧版的循环是：

```
读状态 → 问模型（带全部聊天历史）→ 执行一个动作 → 把结果追加进历史 → 再问
```

三个致命问题：

1. **token 爆炸**：每轮都要把整段历史重发一遍。系统提示 2000 字符 + 每轮新增 800 token，
   累计 ≈ `1400R + 400R²`；**约 140 轮就把 800 万输入额度烧完**，而比赛有 8 小时。
2. **慢**：每次动作都要等一次网络往返（1~3 秒），8 小时做不了多少事。
3. **容易跑偏**：模型一次只看到一个动作的结果，缺少「一串事做完」的连续性。

现在的循环是：

```
读状态 → 问模型「下一个技能」→ 技能内部连续做几十个动作 → 只把摘要回给模型
```

同样 8 小时，模型调用次数从「几千次」降到「几百次」，每次上下文从「几万 token」降到「约 1k token」。

## 三、每个文件干什么

### `main.py` —— 入口

| 命令 | 做什么 |
|---|---|
| `run` | 登录 → 等 ready → 加载状态 → 交给 Agent 跑 |
| `test-api` | 给模型发一句话，打印回复和 usage |
| `test-mc` | 登录 → 等 ready → 打印状态/背包/进度/事件 |
| `status` | 登录后打印当前状态 |
| `mock` | 假服务器 + 假大脑跑 N 轮（离线自检） |
| `reset` | 清空本地状态 |

`build_backend()` 里有一段**注释掉**的代码：以后接自己的服务器时打开就行。

### `config.py` —— 配置

所有开关都在这里，**不含密钥**（密钥放 `.env`，启动时自动读）。

关键项：

| 配置 | 含义 | 默认 |
|---|---|---|
| `LLM_BASE_URL / LLM_MODEL / LLM_API_KEY` | 模型接口 | 从 `.env` 读 |
| `INPUT_TOKEN_BUDGET / OUTPUT_TOKEN_BUDGET` | 比赛额度 | 800 万 / 150 万 |
| `COMPETITION_END` | 当天几点收工 | `18:00` |
| `EAT_BELOW_FOOD` | 饥饿低于多少吃东西 | 14 |
| `FLEE_BELOW_HEALTH` | 血量低于多少逃跑 | 6 |
| `ADVANCEMENT_REFRESH_S` | 多久刷一次进度 | 90 秒 |
| `DECISION_MIN_INTERVAL` | 两次决策最小间隔 | 0（不限） |
| `FAIL_BLACKLIST_COUNT / SECONDS` | 连续失败几次拉黑 | 2 次 / 240 秒 |

### `llm.py` —— 大模型客户端

- OpenAI 兼容（DeepSeek / AIA 代理都能用）；
- **计量**：每次调用累计 `input/output` tokens；
- **预算**：到 98% 抛 `BudgetExceeded`，主循环体面收手；
- **重试**：429/5xx/超时指数退避；401/402 立刻报错并给中文提示；
- **JSON**：支持 `response_format`，代理不支持时自动降级；自带容错解析（能从一段废话里抠出 JSON）。

### `planner.py` —— 规划

- 系统提示里写清：计分规则（只看难度）、**虚空岛限制**、技能清单、决策原则；
- 用户消息只有一小段 JSON：坐标/血量/饥饿/背包/目标/候选进度/岛屿勘察/最近失败/剩余时间和 token；
- 要求模型只输出 `{"skill","args","target","why"}`；
- **模型不靠谱时**有本地兜底：先勘察岛屿 → 饿了吃 → 没木头砍树 → 没镐做镐 → 挖石头。

### `skills.py` —— 技能（核心）

| 技能 | 干什么 | 大概多少次 API 动作 |
|---|---|---|
| `survey` | **勘察自己的虚空岛**：识别村庄/要塞/堡垒/试炼密室/古城等 | 1~2 |
| `scan` | 看周围方块/生物 | 2 |
| `chop_tree` | 找树、走到树下、自下而上挖一整棵 | 5~15 |
| `collect` | 采集某类方块 N 个（木头/石头/煤/铁/钻石…） | 5~40 |
| `craft` | 合成，**缺料自动递归补、缺工作台自动放** | 2~20 |
| `smelt` | 熔炼（放燃料+原料→等→取成品） | 5~10 |
| `eat` | 吃东西 | 1~2 |
| `equip` | 装备最好的工具/指定物品 | 1 |
| `place` | 放方块（工作台/熔炉/箱子） | 1~3 |
| `attack` | 打最近的怪 | 1 |
| `flee` | 远离最近的怪 | 1~3 |
| `explore` | 朝某方向走一小段（虚空岛：**最多 24 格**，防掉虚空） | 1 |

技能里已经处理了这些「脏活」：

- 走不到方块（`No path`）→ 自动试四个相邻格；
- 挖了没捡到（`gained` 为空）→ 记失败、换下一个，不会死磕；
- 合成缺料 → 用服务器返回的 `example_recipe_needs` 递归补齐；
- 需要工作台 → 自动合成 + 放下 + 重试。

### `agent.py` —— 主循环

一圈做四件事：

1. **观察**：`/status`、`/inventory`（带缓存）、`/events`、`/advancements`（限频）；
2. **保命**：饿了吃、血少跑、连续死亡主动休息（躲「死亡循环保护」强制下线 5 分钟）；
3. **决策**：调 Planner；预算不够/模型报错就用兜底；
4. **执行**：调技能，记录耗时、结果、失败；连续失败两次就拉黑该「技能+参数」240 秒。

还负责：掉线重连、token 失效重登、`ready=false` 等待、Ctrl+C 收尾、到点收尾、状态落盘。

### `world_state.py` —— 世界状态与记忆

存三类东西：

- **当前状态**：坐标、血、饥饿、维度、背包、手持；
- **世界知识**：已完成进度（含分数）、候选进度、路点（工作台/熔炉）、失败记录、黑名单；
- **运行账本**：token 用量、轮数、各技能次数、死亡时间。

每圈结束原子写盘（先写临时文件再替换），所以**进程被杀也不会写坏**，重启接着跑。

### `advancements.py` —— 计分

规则（草案 v2，见 `Doc/RULES.md`）：**单项分只看难度**，1/2/3/4/5 → 5/15/30/60/100；根节点 0 分；标「—」的不计分。

- `Codes/data/advancement_scores.json` 是**从 `RULES.md` 自动生成的官方表**：99 项计分、合计 3385 分；
- 表里有 `score` / `scored` 字段，不计分项直接 0 分，**不会进候选**；
- 表里没收录的，按 `frame`（task/goal/challenge）估难度给分（近似，仅兜底）。

> 注意：早期公告里的「+5×深度」已在 v2 取消；如果官方再改表，重新生成这个 JSON 即可，代码不用动。

### `trajectory.py` —— 轨迹与总结

- `logs/run-*.jsonl`：每行一个事件（决策/技能/进度/错误/收尾），带时间戳；
- `任务记录.md`：人类可读的总结（用时、轮数、新完成进度、token、死亡次数）。

### `mc_api.py` / `my_server/` —— 手脚

- `mc_api.McApi`：比赛服 NMO 接口（v1.3），统一 `{ok, result}` / `{ok:false, error}` 处理；
- `my_server.MyServerApi`：**同一套方法名的适配器**，用来接你自己的服务器。切换只改 `main.build_backend()` 里两行（默认注释）。

### `mock_api.py` —— 离线自检

- 假服务器：一小片世界（树、石头、煤、铁）、背包、合成表、熔炉、advancement 触发；
- 假大脑：按剧本返回决策；
- 用途：不联网验证「技能 + 主循环 + 状态 + 日志」全链路。

### `supervisor.py` —— 守护进程

崩溃/退出自动拉起 `main.py run`，到点退出；连续 3 次「刚启动就退出」会停下并提示先排查账号/预算。

## 四、数据流：以「做一把石镐」为例

1. **观察**：`/status` 显示背包 `{oak_log: 4}`，`/advancements` 里 `story/upgrade_tools` 未完成；
2. **决策**：模型输出 `{"skill":"craft","args":{"item":"stone_pickaxe"}}`；
3. **执行**：`craft_chain` 先试 `/craft stone_pickaxe`；
   - 服务器回 `missing_ingredients`（要 3 圆石 + 2 木棍）；
   - 递归合成木棍（要木板 → 要原木），再合成木板；
   - 还缺圆石 → 技能返回失败，下一轮模型改调 `collect group=stone`；
4. **采集**：`collect` 找石头 → 走到旁边 → 挖 3 个 → 确认背包 +3 圆石；
5. **再决策**：模型再调 `craft stone_pickaxe` → 成功；
6. **记账**：`/advancements` 刷新，`upgrade_tools` 完成，+20 分，写进状态和轨迹。

## 五、token 是怎么省的

| 手段 | 效果 |
|---|---|
| 状态压缩（只发关键字段） | 每圈约 250 字符，而不是几 KB |
| 不重发历史 | 上下文恒定，不随轮数增长 |
| 技能宏动作 | 一次决策干几十个动作 |
| 观测节流（背包缓存、进度 90 秒） | 少几次 HTTP，也少几段文本 |
| 决策间隔可调 | 紧张时调大，省 token |
| 预算熔断 | 98% 主动收手，保留收尾的额度 |

粗算：一次决策约 1k tokens，8 小时按 1000 次决策 ≈ 100 万 tokens，远低于 800 万；
真正先耗尽的会是**输出额度**或**时间**，不是输入。

## 六、错误处理策略

| 错误 | 谁处理 | 怎么处理 |
|---|---|---|
| `busy` | `mc_api` / 技能 | 等 0.6 秒重试（最多 3 次） |
| `path_not_found` | 技能 | 换相邻格再试；仍不行就失败 |
| `missing_item` / `missing_ingredients` | 技能 | 递归补料；补不了就失败，让模型换目标 |
| `need_crafting_table` | 技能 | 自动合成 + 放工作台 + 重试 |
| `wrong_server` / `not_connected` | Agent | 重连 + 等 ready |
| `invalid_token` | Agent | 重新登录 |
| `death_loop_cooldown` | Agent | 主动休息 5 分钟（避免更糟） |
| 429 / 5xx / 超时 | `llm.py` | 指数退避重试 |
| 预算用尽 | `llm.py` | 抛 `BudgetExceeded`，Agent 收尾 |

## 八、学习层与决策层（v3）

- 学习层 `Codes/learn.py`：`python main.py learn --minutes 20`；
  LLM 做实验 / 问用户 / 写 `state/knowledge.json/md`，**不冲分、不读 strategy**；
- 决策层 `Codes/agent.py` + `planner.py`：`python main.py run` 读 memory 摘要和 `data/strategy.md`，
  按你的策略做比赛决策；
- 两个模式共享 `world_state.json`，但 memory 独立；详细说明见
  [`学习层与决策层.md`](学习层与决策层.md)。

策略不再预设 phases/targets：默认 `strategy.json` 为空；推荐写 `data/strategy.md`（自由文本），
LLM 自己拆解。`python main.py strategy` 查看当前策略。
