# 配方与合成：为什么老有“被拒绝的配方”

> 结论先说：**配方书本身是确定的，但同一个物品往往有多条配方；以前本地桥只拿“第一条”，所以经常选到一条你背包里做不了的配方。**
> 现在已改成：遍历所有配方 → 按当前背包 + 请求数量算缺口 → 选真能做的那条。

---

## 1. “配方书”到底是哪来的

| 环境 | 配方来源 |
|---|---|
| 比赛方接口 | 主办方服务端的 Mineflayer/版本注册表，`craft` 由他们选配方 |
| 本地 `local_bot` | 你连接的 Minecraft 版本的客户端注册表，`bot.recipesAll()` |
| 本项目的 `craft_chain` | 不维护配方表，只根据服务端返回的 `missing_ingredients` 递归补料 |

所以：
- **不是我们手写了一份配方表**（除了技能里的少量默认补料顺序）；
- 配方由 Mineflayer 从游戏注册表读取，版本一致就一致；
- 但“选哪条配方”是代码逻辑，选错就会看起来像“配方被拒绝”。

---

## 2. 为什么会有多条配方

同一个物品常常有多个合法配方：

- `oak_planks`：橡木、白桦、云杉、丛林、金合欢、深色橡木、红树、樱花、竹……每种原木一条；
- `stick`：每种木板各一条；
- `crafting_table`：每种木板各一条；
- 工具/箱子等：同样按木种分。

如果你背包里是 **白桦原木**，而代码拿的是 **橡木配方**，就会报：

```
missing_ingredients: 材料不够合成 oak_planks
example_recipe_needs: {"oak_log": 1}
```

你明明有木头，却被告知缺橡木——这就是“被拒绝的配方”。

---

## 3. 旧逻辑的三个 bug

### 3.1 只拿第一条

```js
const recipe = all.find((r) => !r.requiresTable) || all[0];
```

`all` 里可能第一条是橡木，你背包是白桦；直接失败。

### 3.2 缺料只按 1 次算

```js
const needPerCraft = -d.count;
if (have < needPerCraft) missing...
```

要合成 4 个，只检查“做 1 个够不够”；结果 `bot.craft(recipe, 4)` 仍然失败。

### 3.3 没有把“缺口”和“总需求”分开

Agent 拿到 `example_recipe_needs` 后按请求数量乘，容易补多或补错；
尤其是中间产物（木板→木棍）会抢原料。

---

## 4. 现在的逻辑（local_bot）

`Codes/local_bot/server.js` 的 `craft`：

1. `bot.recipesAll(def.id, null, true)` 拿到该物品的全部配方；
2. 对每条配方：
   - 按 `count / 单次产量` 算 `times`；
   - 用 `recipe.delta` 算“当前背包做 `times` 次还差多少”；
   - 记录缺口总和 `score`；
3. 优先选 **score=0 且不需要工作台** 的配方；其次 score=0 需要工作台的；
4. 都做不了时，选缺口最小的，返回：

```json
{
  "code": "missing_ingredients",
  "example_recipe_needs": {"birch_log": 1},
  "missing_total": {"birch_log": 2},
  "recipe_result_count": 4,
  "alternatives": 9
}
```

- `example_recipe_needs`：单次合成的完整用料（兼容旧字段）；
- `missing_total`：按本次请求数量算出的**还差多少**（Agent 直接补这个数）；
- `alternatives`：这个物品共有多少条候选配方，方便排查。

`Codes/skills.py` 的 `craft_chain` 会优先用 `missing_total`：
- 有 `missing_total`：直接补缺口，不再乘 `count`；
- 只有 `example_recipe_needs`（比赛服旧字段）：沿用“按数量缩放”的兼容逻辑。

---

## 5. 为什么比赛服也可能“拒绝”

即使本地修好了，比赛方仍可能返回：

| 错误码 | 含义 | 你该做什么 |
|---|---|---|
| `missing_ingredients` | 它选的配方缺料 | 看 `example_recipe_needs`，补对应材料；或先做中间产物 |
| `need_crafting_table` | 配方需要 3x3 | 先 `craft crafting_table`，再 `place` |
| `no_recipe` | 该物品没有配方/名字写错 | 检查物品 id（不带 `minecraft:` 前缀） |
| `bad_args` | 参数错 | 检查 `item`/`count` |

比赛方选配方的逻辑不公开；如果它偏偏选了另一条木种配方，你只能：
1. 把 `example_recipe_needs` 里的材料补上；
2. 或者先合成它要的中间产物；
3. 记录到 memory，下次避开。

> 这不是“配方书错了”，而是“多条合法配方 + 选哪条”的差异。

---

## 6. 怎么快速判断

```bat
:: 看最近一次运行的合成失败
python main.py report

:: 看轨迹里的 skill 错误
findstr /i "missing_ingredients need_crafting_table no_recipe" logs\run-*.jsonl
```

常见对照：

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 有白桦却说要橡木 | 旧桥选第一条配方 | 更新 `local_bot/server.js` 并重启桥接 |
| 要 4 个却只检查 1 个 | 旧桥没乘 `times` | 同上 |
| 合成台放不下 | `place` 失败/周围没空间 | 换位置，或先 `scan` |
| 工作台有了还说需要 | 工作台不在 4 格内 | 靠近工作台，或重新 `place` |
| 同一个 craft 反复失败 | `craft_chain` 补料循环 | 看 `failure/blacklist`，换目标或先 `collect` |

## 7. 验证方法（本地）

1. 清空背包，只留 **白桦原木**；
2. 执行 `craft oak_planks count=4`（本地桥会把它映射到白桦配方）；
3. 期望：成功，`gained=4`，不再报 `oak_log` 缺失；
4. 再试 `craft stick count=4`：应自动用白桦木板；
5. 看 `logs/run-*.jsonl` 里 `skill=craft, ok=true`。

> 如果仍失败，先确认 `local_bot` 已重启（改的是 Node 代码，不重启不生效）。
