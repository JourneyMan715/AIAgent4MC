## 0. 结论先说

**代码本身能跑（`python main.py` 跑通了砍树→合成工作台），但它不是这个赛道要的东西。**

三句话概括：

1. **评分口径完全没对上**：比赛 60 分是「advancement 完成分」，而这个项目里 `/advancements` 接口写了却**从没被调用过**，目标还是写死的一句「砍树合成工作台」——这条任务在计分表里大概值 2 个低难度进度，接近 0 分。
2. **架构形态不适合 8 小时无人值守**：主循环每做完一个任务就 `input()` 等人打字；单任务 50 轮上限；每做**一个动作**就问一次大模型、并且把整段历史重发一遍。按现在的 token 消耗速度，**约 120~140 轮（≈400 次动作）就会把 800 万输入额度烧完**，而比赛有 8 小时。
3. **合规与工程交付有硬伤**：模型地址直连 `api.deepseek.com` + 个人 key，违反「必须走 AIA 统一代理」；两个入口 `test-api` / `test-mc` 直接 `NameError` 崩溃；`Codes/requirements.txt` 被删导致教程第一条命令就失败；API key 与 Bot 密码明文进了 git。

如果按现状提交：游戏表现分大概率垫底（0~60 分里的个位数），工程评审分（40 分）会因为「入口跑不起来 + 无测试 + 无日志 + 文档自相矛盾」而明显扣分。

**距初赛（11 月 22 日 10:00–18:00）还有 9 天**，问题都可修，但优先级必须重排。

## 2. P0：阻断性问题（不修就基本没分 / 有合规风险）

### P0-1 违反赛道规则：模型没有走 AIA 统一代理

- 现状：`Codes/config.py:17` 写死 `API_BASE_URL = "https://api.deepseek.com/chat/completions"`，`Codes/config.py:11` 是个人 `sk-` key，`deepseek_client.py:27` 直接 POST。
- 规则原文（Harness 赛道第 1 条）：
  > 统一模型；接入 AIA 提供的统一代理 API；**不得改用其他大模型或通过外部服务绕开额度约束**。
- 后果：这不是「优化项」，是**合规项**——最轻是被判违规，最重是取消成绩。而且额度是按代理返回的 usage 统计的，直连就完全没有额度概念。
- 必须做：改成可配置的 `base_url` + `model` + 队伍密钥；所有调用带上 usage 统计；本地做 800 万/150 万的预算器（到 70%/90% 降级，到 100% 停手并保存状态）。
- 现状还缺：`DeepSeekClient.chat()` **不返回 usage**（`deepseek_client.py:42-46` 只取 content），所以你连自己用了多少 token 都不知道。

### P0-2 目标函数错位：不读 advancement，等于不看计分板

- 规则：游戏表现分 = 8 小时内所有**原版非配方 advancement** 的分数和；难度基础分 5/15/30/60/100，再加 `5 × 进度树深度`；同分时先比难度 5 的数量、再比难度 4。
  （**注**：2026-11-13 收到的草案 v2 已取消「5 × 深度」，改为只看难度；本项目已按 v2 适配，见 `Doc/RULES.md` 与 `Codes/data/advancement_scores.json`。本节保留重构前的诊断原貌。）
- 现状：
  - `mc_api.py:148-154` 写了 `advancements()`，但 **全项目没有任何地方调用它**（`grep` 只命中定义处），也没暴露成工具（`tools.py` 的 20 个工具里没有 `advancements`）。
  - 更讽刺的是 `/advancements` 的 `include_recipes` 参数，正好对应规则里「配方解锁不计分」——接口就是按计分口径设计的，却没接。
  - `config.py:32` 的 `GOAL` 是一句自然语言任务，程序没有任何「目标价值」概念；`run_one_task` 完成后只凭模型一句 `stop` 就判定「✅ 正常完成」。
- 后果：Agent 不知道自己在比赛里该干什么、干了值多少分、还差什么。8 小时大概率只走到「木头 → 石镐 → 铁」这条人人都有的浅层路线。
- 必须做：把 `/advancements` 作为**唯一的进度真值**（定期轮询 + 事件补充），建立「advancement 计分表」（难度×深度），把主循环改成「选目标 → 执行 → 校验进度增量 → 记分 → 换目标」。

### P0-3 必须人肉驱动，撑不起 8 小时

- 现状：
  - `main.py:414` `line = input("你说：")` —— 每个任务结束都停下来等人打字；
  - `main.py:453` 单任务最多 `MAX_STEPS=50` 轮，到上限就结束回命令行；
  - 没有全局时钟（不知道 8 小时还剩多少）、没有「比赛开始/结束」状态、没有 supervisor 自动重启（规则明确允许重启程序）、没有断线/卡死看门狗。
- 规则：比赛 8 小时，程序中断也算时间，不补时；「禁止参赛人员直接代替 Agent 执行游戏行为」——靠人一句话一句话喂目标的形态，既不自主，也不现实（人不可能守 8 小时）。
- 必须做：无人值守主循环：目标队列自动生成 → 执行 → 校验 → 下一个；`supervisor` 进程守护（崩溃自动拉起、从状态文件恢复）；到 18:00 硬停 + 保存最终 advancement 快照。

### P0-4 Token 经济性：按现在的写法，预算会在一两个小时内烧完

这是最容易被忽略、但**数学上必然发生**的问题。

**实测**：`build_system_prompt()` = 2002 字符（其中工具清单 1190 字符），中英混合约 **1200~1400 tokens**，而且**每一轮都整段重发**。

**估算模型**（保守）：
- 每轮新增内容 ≈ 状态摘要 100 + 模型回复 100 + 平均 3 个动作的反馈 3×200 ≈ **800 tokens**；
- 第 r 轮的输入 ≈ `1400 + 800 × (r-1)`；
- 累计输入 ≈ `1400 × R + 400 × R²`。

| 轮数 R | 累计输入 tokens | 说明 |
|---|---|---|
| 50 | ≈ 1.1 M | 一个任务的上限 |
| 100 | ≈ 4.1 M | |
| **140** | **≈ 8.0 M** | **输入额度耗尽** |
| 200 | ≈ 16 M | 超支 2 倍 |

也就是说：**约 140 轮、400 来次动作之后，就没有 token 再问模型了**。而 8 小时里本可以做几千次动作。输出额度（150 万）反而不是瓶颈。

根本原因：**「一个动作 = 一次全量对话」**。而且历史消息从不裁剪（`main.py:467` 每轮 append，`messages` 只增不减），既贵又迟早超上下文。

必须做（三件事一起）：
1. **状态压缩**：每轮只发「结构化状态（坐标/背包/进度/危险）+ 最近 3 条结果 + 计划」，历史做滑窗 + 摘要，目标 **≤1.5k tokens/次决策**；
2. **技能层（宏动作）**：把「砍一棵树」「挖一条矿道」「做一套木石工具」写成确定性代码，一次决策执行 20~50 个 API 动作，而不是一个 `dig` 问一次模型；
3. **预算器**：记录每次 usage，实时显示剩余额度与预计可跑时长。

## 3. P1：行为层问题（有实跑证据）

以下全部来自 `Workflow/flow.md` 一次真实运行（6 个任务、58 轮、103 次动作）：

| 指标 | 数值 |
|---|---|
| 决策轮数 | 58 |
| 实际动作 | 103 |
| 失败动作 | 14（13.6%） |
| `move_to` 报 `No path to the goal!` | 5 次 |
| `dig` 成功 | 26 次 |
| 其中 `gained: {}`（挖了但没拿到东西） | **11 次（42%）** |
| `get_block` 单点查询 | **27 次（占全部动作 26%）** |
| 反思触发 | 2 次 |

### 3.1 计划执行不校验失败，失败还继续往下做（最影响效率的 bug）

`main.py:484-491`：

```python
for action, args in plan:
    ...
    ok, feedback = call_action(api, action, args)   # ← ok 拿到手就丢掉了
    messages.append({"role": "user", "content": feedback})
```

`ok` 从未被使用，所以一步失败后**剩下的步骤照做**。日志里非常典型（flow.md:75-83）：

```
第 2 轮 {"steps": [move_to, dig, dig, dig]}
  move_to 失败：No path to the goal!
  dig 失败：No path to the goal!      ← 明知到不了，还挖了三次
  dig 失败：No path to the goal!
  dig 失败：No path to the goal!
```

每次失败要 8 秒级超时 + 一轮 token，纯粹浪费。修法：**任何一步失败立即中止本计划**，把失败原因和「已完成的步骤」一起回给模型重新规划。

### 3.2 没有失败记忆，同一个坑反复踩

实际发生：模型连续 6、7 轮对同一棵树的树叶/原木做 `get_block` → `dig` → `move_to`（flow.md:106-159），其中多次是**同一个坐标同一个动作**。程序侧没有任何「这个 (action, args) 已经失败 N 次」的拦截或提示，只能靠模型自己想起来。

修法：动作签名去重 + 失败计数，≥2 次就把「该动作已失败，换目标/换方法」写进上下文；并把「已失败的坐标」放进结构化状态。

### 3.3 「走不到那个方块」是设计缺陷，不是模型笨

`find_blocks` 返回的 `pos` 是方块坐标（含 y），模型按提示词「观察到的坐标可以直接原样回填」直接塞给 `move_to`，而 `move_to` 带 y 时会尝试走到「方块所在格」——树叶/树干内部当然无路可走。日志里 5 次 `No path` 全是这个原因。

修法：
- 加 `approach_block(pos, range=2)` 技能：只取 x/z、忽略 y、自动选相邻可站点；
- 提示词明确「`move_to` 一般不要带 y；方块坐标先 approach 再 dig」；
- 对 `No path` 做自动降级（去掉 y 重试一次）。

### 3.4 没有「区块/地图/资源」记忆，全是重复劳动

- `find_blocks` 半径最大 64、`get_entities`最多 40 个，接口不提供「结构定位」；
- 程序没有本地地图：不知道家在哪、哪片树林砍过、哪个矿洞下去过、基地方向；
- 于是每次换任务都要重新 `find_blocks` 一遍（日志里 6 个任务反复扫同一片林子）。

修法：本地建一张**稀疏网格地图**（chunk → 已探明资源/地形/危险）+ 路点（家、矿口、床、传送门）。这也是评审眼里的「状态维护」。

### 3.5 缺宏观技能层，导致「砍树」要 13 轮

日志第 2 个任务：为了砍一棵橡树，模型先挖树叶（8 轮 24 次动作）、再试 `get_block` 探树干、再 `move_to` 卡住……**13 轮才拿到 3 块木头**。

这不是模型的问题——把「找树→定位树干最低那节→走到侧面→自下而上挖 4~6 节→捡掉落→确认背包增量」写成一个 `chop_tree()`，20 秒就完了，几乎不耗 token。

同类缺失：`mine_tunnel`、`craft_chain`（带配方预检）、`smelt`、`get_food`、`place_safe`、`bridge`、`trade`、`breed`、`portal`。

### 3.6 动作结果被截断成非法 JSON，模型看到的是残缺数据

`main.py:207-209`：

```python
text = json.dumps(result, ensure_ascii=False)
if len(text) > 400:
    text = text[:400] + "…"
```

日志中真实出现（flow.md:12）：

```
find_blocks 结果：{"total": 327, "blocks": [{"name": "oak_log", ... {"name": "oak_log", "pos": [3, 110, 0]…
```

`total: 327` 但只能看到 4 个、JSON 还是断的。同时 `dig`/`craft`/`place` 这类模板化结果其实只需要两三个字段，没必要整段 JSON。

修法：**按接口做结构化摘要**（块列表只留 name/pos/dist，最多 5 条；craft 只报 crafted/gained/inventory 变化），并且永远输出合法 JSON。

### 3.7 记忆/自进化基本是装饰

- `lessons` 只在**每 10 轮**反思一次，输入只有「最近 8 条 user 消息」（`_build_reflect_context`），没有成败标签，产出是「砍树时应直接锁定树干原木而非先挖树叶」这种**人尽皆知的空话**（日志 2 条全是这类）；
- 这些空话每轮都追加进系统提示词（`main.py:61-63`），**只花 token、几乎不改行为**；
- `plan` 只有「目标变了」才重算（`main.py:438`）；同一目标重跑时**沿用上次的计划**，哪怕上次已经失败、位置/背包/世界都变了（日志第 3 次运行就出现「任务目标和上次相同，沿用已有计划」）；
- `goals_history` 把闲聊也当目标存（「请问你砍了多少木头？」「？我让你去砍树，你执行了半天在干啥？」），污染上下文；
- 更严重的是**记忆里没有世界状态**（背包、进度、坐标、基地），重启即失忆。

### 3.8 聊天和任务混在一起，答非所问（已在日志里暴露）

- `classify_input()` 把「？我让你去砍树，你执行了半天在干啥？」判成 **task**，于是真的去砍树了（flow.md:458-529）——用户问的是「你在干啥」；
- 真正的聊天回答**看不到背包**（只喂了 `summarize_status`），于是出现（flow.md:446）：
  > 「我还没开始砍呢，现在手上一根木头都没有～」
  而上一轮 `inventory` 明明有 7 块 `oak_log`（flow.md:426）。**Agent 在向用户撒谎**——这在「可观赏性/直播」维度是硬伤。
- 修法：聊天回复也带上完整状态（含背包/进度）；分类器改成「先判断是否提问」；比赛现场根本不需要这个交互，直接砍掉。

### 3.9 生存策略缺失，随时可能触发「死亡循环保护」

- 日志里血量 11/20、饥饿提示「有点饿」，**全程没有吃东西、没有逃跑、没有避夜**；
- 接口规则：**60 秒内死 3 次，Bot 强制下线 5 分钟**。8 小时里挨两次就是 10 分钟空转，还会被别的队抢资源；
- 现在 `_RECOVER["death_loop_cooldown"]=30` 只等 30 秒就放弃，任务直接结束回命令行。

修法：状态机里加安全层——`food < 14 自动吃`、`health < 8 撤退/搭墙`、`夜晚有敌对生物就挖三格躲`、死亡后读 `last_death`/`dropped_items_at` 决定是否捡尸。

### 3.10 观测面太窄，`/status` 一半字段被丢掉

`summarize_status()`（`main.py:172-201`）只用了坐标/血/饿/手持/岩浆/着火/敌对/维度/昼夜/效果，丢了：
`ready`、`busy`、`xp_level`、`xp_progress`、`armor_points`、`saturation`、`in_vehicle`、`is_sleeping`、`oxygen`、`on_ground`、`biome`、`time_of_day`、`last_death`、`offhand`、`blocking/sneaking`。

其中 `xp_level`（附魔台要 30 级）、`biome`（探索类进度）、`ready`（大厅/比赛服）都是**直接影响决策**的。而背包要单独再发一次请求（每轮多一次网络往返）。

### 3.11 事件流写了不用

`mc_api.py:139-146` 的 `events()` 和 `last_seq` 游标没有任何调用点。等于放弃了 `hurt`（谁打我）、`death`、`pickup`、`chat`、`death_loop`、`server_confirmed` 这些**免费且低 token** 的感知通道——明明可以「被动感知」，现在全靠主动轮询。

### 3.12 错误处理粗糙

| 位置 | 问题 |
|---|---|
| `mc_api.py:28` | 所有接口统一 `timeout=90`；`move_to` 长距离、`use_item` 钓鱼（30s）可能超过 90s → 客户端超时，但**服务端动作还在跑**，下一条就是 `busy`，状态错位 |
| `main.py:214-221` | `busy` 只等 0.6 秒 × 3 次 ≈ 1.8 秒；真实动作常持续 10 秒以上 → 必然失败 |
| `deepseek_client.py` | 429/5xx **没有退避重试**，`main.py:470-473` 直接 `break` 结束整个任务 —— 8 小时里一次限流就废一个任务 |
| `main.py:226` | 重试逻辑只认 6 个错误码，`interrupted`/`timeout` 一律当失败回给模型（其实 `interrupted` 自带 `interrupted_by` 和 `nearest_hostile`，应触发「先保命」） |
| `main.py:507-510` | `api.stop()` 包在 `except Exception: pass` 里，失败静默 |

### 3.13 提示词/解析工程弱

- `_extract_json` 用贪婪正则 `\{.*\}`（`main.py:132`）：模型一旦输出两段 JSON、或字符串里有花括号、或被 `max_tokens=400` 截断，就解析失败；失败后只是补一句「请严格按 JSON 格式输出」，**没有次数上限**，可以耗完 50 轮；
- `temperature=0.7`（`deepseek_client.py:14`）用来做「选动作」太随机；应 0~0.2，并开 `response_format={"type":"json_object"}`；
- 20 个工具只有一行中文说明，**没有参数 schema**：`window_act` 的 `ops` 结构、`use_item` 的 `target` 写法全靠猜；
- 没有 few-shot、没有「坐标是方块格不是站点」「不要给 move_to 传 y」「place 不传 pos 会自动选位」这类关键约束；
- `tools.dispatch` 直接把 `**args` 透传给 `mc_api`，参数名错就抛 `TypeError`，把 Python 报错原文喂给模型。

## 6. 建议的目标架构（v2）

现在的问题是「把 LLM 当 tick 级控制器用」。应该改成 **LLM 低频率做战略决策，确定性代码做战术执行**：

```
┌──────────────── supervisor（守护进程，独立于主程序）────────────────┐
│  8h 时钟 / 比赛阶段 / 崩溃拉起 / 状态文件恢复 / 到点硬停 + 快照     │
└───────────────┬────────────────────────────────────────────────────┘
                │
   ┌────────────▼─────────────┐   每 5~15 秒轮询（≤4 并发）
   │ 感知层 Observer          │◄── /status /inventory /events /advancements
   └────────────┬─────────────┘
                │ 结构化 WorldState（坐标/背包/进度/危险/时间）
   ┌────────────▼─────────────┐
   │ 世界模型 WorldModel      │  本地持久化：稀疏地图、路点、已得进度、
   │ （状态维护 + 记忆）       │  失败动作表、配方知识、token 账本
   └────────────┬─────────────┘
                │ 每 ~30~90 秒一次「战略决策」（≤1.5k tokens）
   ┌────────────▼─────────────┐
   │ 规划层 Planner (LLM)     │  选下一个 advancement 目标 + 选技能 + 参数
   └────────────┬─────────────┘
                │ 技能调用（不是 API 调用）
   ┌────────────▼─────────────┐
   │ 技能层 Skills（纯代码）   │  chop_tree / mine_tunnel / craft_chain /
   │ 20~50 个 API 动作/次      │  smelt / eat / flee / place_safe / bridge /
   └────────────┬─────────────┘  trade / breed / portal / fish / sleep
                │
   ┌────────────▼─────────────┐
   │ 执行层 Executor          │  重试/降级/中断处理/事件订阅/动作去重
   └────────────┬─────────────┘
                │
            NMO Bot API（v1.3）
```

要点：

1. **技能层是分数和 token 的双重杠杆**：一次决策干 20~50 个动作，8 小时能做的事量级提升，同时 token 降到 1/10。
2. **advancement 驱动**：`/advancements`（`include_recipes:false`）作为唯一真值；本地维护「已完成/可做/需要什么」表；每完成一项立刻记账，定期重算「下一分从哪来」。
3. **计分表内置**：难度×深度 → 分数，按 `分数 / 预计耗时` 排序选目标。没有官方计分表就先用社区数据近似，拿到官方的再替换。
4. **世界模型**：家/床/矿口/农场路点、chunk 资源网格、危险区、已得进度、失败记录、token 账本，全部落盘，重启可续。
5. **安全层**：吃/逃/躲夜/不触发死亡循环；`hurt` 事件优先级最高。
6. **预算器**：按代理返回的 usage 记账，70% 降级（少问模型、多跑技能）、100% 停手保存。
7. **可观测**：JSONL 轨迹（每步动作+结果+token）、每 15 分钟落一次 advancement 快照、生成「分数曲线」和「高光时刻」——这既是比赛复盘，也是评审材料。
